## [Stage 8.4] Price категоризатор слишком гранулярный

**Симптом:** на лидах с малым числом услуг (~6) и широким разбросом по типам
(маникюр + педикюр + макияж + причёски + брови) Price-таблица фрагментируется:
5 групп × 1 элемент. Заголовки категорий доминируют над содержимым,
выглядит рвано.

**Пример:** kalinka-58 (6 услуг, 5 категорий после `_categorize_price_item`).

**Где:** `config_builder/builder_v2.py`, функция `_categorize_price_item` +
логика формирования groups в `_build_price_section`.

**Возможные направления (не выбрано):**
- Сливать группы из 1 элемента в "Прочее"
- Минимальный размер группы = 2, иначе в "Прочее"
- При groups_count > items_count/2 — рендерить плоским списком без заголовков
- Пересмотреть гранулярность самих категорий (объединить Маникюр+Педикюр в "Ногти" и т.п.)

**Приоритет:** низкий. Не блокирует, проявляется только на узком классе лидов.
**Связано с:** Stage 8.4 коммит #1 (условный рендер Price).

## [Stage 8.4] Несогласованные контракты "пустой секции"

**Симптом:** разные секции при отсутствии данных ведут себя по-разному:
- Price (`_build_price_section`) — возвращает `None`, секция выпадает из `sectionsOrder` 
- Gallery (инлайн в главной функции, ~стр. 256) — остаётся в `sections` с `enabled: false` 

**Последствие:** фронтенд должен поддерживать оба варианта (пропуск отсутствующей
секции и пропуск секции с `enabled: false`). Это работает, но удваивает поверхность
для багов и затрудняет рефакторинг порядка секций.

**Возможные направления (не выбрано):**
- Привести всё к "возврат None из билдера + фильтрация sectionsOrder"
- Привести всё к "всегда есть в sections, фронт смотрит на enabled"
- Оставить как есть и явно задокументировать какой контракт у какой секции

**Приоритет:** средний. Не ломает текущие лиды, но создаёт мину при расширении.
**Связано с:** Stage 8.4 коммиты #1 и #2.

## [Stage 8.4] FAQ источник нарушает принцип "не придумываем"

**Симптом:** блок FAQ на лендингах рендерится из контента,
сгенерированного LLM (curator AI). Это противоречит базовому принципу
проекта "Максимум копирования, минимум генерации" — мы не должны
выдумывать ответы на вопросы, которые клиенты салону не задавали.

**Текущий статус:** блок ВРЕМЕННО оставлен видимым по решению владельца —
для визуальной оценки лендинга целиком. Это не одобрение источника,
а отложенное решение.

**Где:** вероятно `llm/content_curator.py` или похожий модуль генерации
FAQ. Проверить точное место при работе над фиксом.

**Возможные направления (не выбрано):**
- Извлекать вопросы из реальных reviews клиентов (NLP по тексту отзывов)
- Парсить FAQ-секцию с TapLink / сайта салона если она там есть
- Брать вопросы из переписки в Direct / WhatsApp если владелец делится
- Если ни один источник не доступен — скрывать блок (как Gallery при <3 фото)

**Что делать сейчас:** ничего. Блок висит для визуала.
**Что делать потом:** выбрать источник из списка выше, реализовать,
переключить FAQ с LLM на реальные данные. Если источника нет —
блок выпадает по тому же контракту что Price/Gallery.

**Приоритет:** средний. Не блокирует текущий релиз, но нарушает
главный принцип проекта и должен быть закрыт до публичного запуска.
**Связано с:** Stage 8.4 (общая ревизия архитектуры секций).
